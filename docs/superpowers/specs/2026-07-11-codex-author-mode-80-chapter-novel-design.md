# Codex 作者模式与 80 章原创小说压力测试设计

**状态：** 已批准  
**批准时间：** 2026-07-11  
**批准方式：** 用户在可视化设计页选择“批准该设计”  
**目标项目：** `AINovel Studio`  
**原创小说工作名：** 《雾城失物招领处》

## 1. 决策摘要

本次不续写现有项目 `lPW4AcWAVYuJ8PCVP-Ip_`，也不让 DeepSeek 承担正文 Writer。现有项目保持原样，作为工作台当前生成质量和审查能力的证据样本。

新建一个独立的 80 章项目，由 Codex 主代理完成题材、设定、五卷大纲、逐章正文和人工修订。子代理只允许执行连续性检查、审稿对照和质量复核，不得代写最终正文。

工作台新增“作者模式”：接收 Codex 或真实人类作者提供的章节，跳过 Writer 调用，复用现有确定性检查、Quick Review、Deep Review、版本、Commit、Canon、Summary、回滚和导出链路。DeepSeek 仅可作为被测 Reviewer 或结构化信息提取器使用。

## 2. 当前证据与问题基线

### 2.1 当前数据状态

- 当前只有一个小说项目。
- 正式章节为 7 章，第 8 章停在 `manual_review`。
- 当前项目硬上限为 28 章；代码静态上限为 200 章。
- 当前共有 4 份持久化 review，覆盖第 4、8 章。
- 当前没有小说导出成品。
- 3 个 Playwright E2E suite、共 12 个用例全部被 `test.describe.skip` 跳过。

### 2.2 当前正文质量证据

主代理已完整阅读现有第 1–7 章和第 8 章草稿。已确认的问题包括：

- 第 3 章内部重复“骨墙—古字—文字漩涡—骨书归还”场景。
- 第 5–8 章反复使用“裂隙—共振—眼睛/印记—追踪—归还”结构。
- 多处角色无过渡离场或重聚，位置与时间连续性不足。
- 多处句子缺少必要主语、谓语或连接词，出现残缺表达。
- 规则主要由旁白或角色直接解释，缺少事件和代价驱动。
- 配角多数只承担解释和递送线索功能，缺少独立目标与反作用力。

### 2.3 当前审查机制证据

- 第 8 章 Quick Review 判定 `pass`，没有识别其与第 7 章的大面积场景复刻、同伴重聚断层、追踪印记重复及空间因果错误。
- 第 8 章 Deep Review 能发现章末总结、句首重复、感官密度和部分规则问题，但仍低估跨章场景重复与逻辑断裂。
- Opening/Mid 强制深审策略可能被前置 Quick Audit 调用门绕过。
- 下一章 Blueprint 可能在上一章 Canon/Summary 同步前生成。
- Review Report 没有绑定正文版本和内容哈希。
- Deep Review 返回的 `earliestAffectedChapter` 没有被限制在实际审查窗口内。
- Canon 的 Summary/Facts/Snapshot 三路提取使用全有或全无的 `Promise.all`，单路失败会使整章退化。

这些问题决定了本次不能只写小说，还必须先建立“外部作者正文进入同一审查闭环”的产品路径，并修复会污染 80 章实验结论的 P0 缺陷。

## 4. 原创新书设计

### 4.1 基本信息

- **书名：** 《雾城失物招领处》
- **类型：** 都市悬疑、民俗异闻、群像成长
- **结构：** 5 卷 × 16 章，共 80 章
- **单章长度：** 2200–3200 个非空白中文正文字符
- **总长度下限：** 176000 个非空白中文正文字符
- **叙事视角：** 第三人称限知，以林砚为主，少量经过明确标记的配角视角章
- **目标体验：** 商业网文的清晰钩子与持续推进，加上可追溯的线索、人物代价和完整结局

### 4.2 一句话故事

雾港火车站的失物管理员林砚，能从遗物中听见失主消失前的最后六十秒。一次无人认领的红伞里，传出了失踪七年的姐姐的声音；与此同时，整座城市开始遗忘那些“从未存在过的人”。

### 4.3 核心主题

- 人是否只有被记录才算存在。
- 记忆的价值不在完整，而在有人愿意承担它带来的责任。
- 寻找亲人不能以把其他人变成证据为代价。

### 4.4 世界硬规则

1. 每件异常遗物只能读取一次“失主消失前的最后六十秒”。
2. 每次读取都会磨损林砚的一段私人记忆，磨损内容不能由他选择。
3. 被城市记录抹去的人，仍能短暂存在于与其有真实情感联系的实体物件中。
4. 每天凌晨 04:17，雾港的档案、监控、门牌和公共记录会自动修正一次。
5. 单纯记住名字不足以救回被抹去者；其存在必须重新进入至少一种可被他人验证的公共记录。
6. 不存在无代价复活。已经死亡的人只能留下证据、影响和选择，不能被规则恢复为活人。
7. 规则信息必须先通过人物遭遇、损失或误判显现，再给出最少必要解释。

### 4.5 主要人物

#### 林砚

雾港火车站夜班失物管理员。谨慎、记性好、习惯给物品贴精确标签。起初把每个失踪者都视为通向姐姐的线索；最终学会先对眼前的人负责，再追索真相。

#### 林见夏

林砚的姐姐，七年前在旧渡轮事故后失踪。她并非等待营救的静态目标，而是在被抹去的城市层中主动维护一批人的存在记录。

#### 苏栖

地方电台夜间节目制作人。擅长声音取证，对“无人认领的来电”有独立调查目标。她与林砚合作，但会反对他为姐姐牺牲无关者记忆。

#### 陈渡

市档案修复中心职员，能看见被系统修正前的纸面残痕。早期帮助主角，之后因家人被抹去而选择与档案局合作，是立场可理解但必须承担后果的对手。

#### 周野

旧城区午夜公交司机，熟悉已经从地图上消失的道路。他知道部分规则，但每次提供帮助都要求对方替一位被遗忘者完成一件现实中的小事。

### 4.6 五卷结构

#### 卷一：雨夜遗物（1–16）

- 建立失物招领处、能力、记忆代价和 04:17 修正规则。
- 红伞案完成第一个独立闭环。
- 林砚确认姐姐的声音不是录音，而是来自被抹去的城市层。
- 卷末代价：林砚失去关于母亲面容的一段记忆。

#### 卷二：无名乘客（17–32）

- 午夜公交和不存在的乘客名单把个人寻亲升级为城市级异常。
- 苏栖的电台成为被抹去者重返公共记录的试验入口。
- 陈渡第一次主动篡改证据，双方关系出现不可逆裂缝。
- 卷末揭示：七年前渡轮事故的死亡名单本身就是一次 04:17 修正产物。

#### 卷三：沉城档案（33–48）

- 主角团进入被旧地图覆盖的沉城街区。
- 揭示异常能力来自一套失败的城市灾难记忆保存工程。
- 林见夏仍在行动，但她正在逐步失去自己的名字。
- 卷末代价：林砚为了保存一批陌生人，主动放弃一段与姐姐有关的关键童年记忆。

#### 卷四：退潮名单（49–64）

- 04:17 修正开始失控，活人也会在白天被公共记录抹去。
- 陈渡成为主要对手，但其目标是让家人回到现实，而非单纯夺权。
- 林砚必须决定是优先完成姐姐的记录，还是先阻止全城大规模失忆。
- 卷末选择：林见夏拒绝用其他人的消失换取自己的回归。

#### 卷五：雾散之前（65–80）

- 回收红伞、午夜公交、渡轮名单、录音母带和档案修正五条核心线索。
- 主角团把私人记忆转换为全城可验证的公共见证，阻断单点删除。
- 陈渡承担其篡改记录造成的后果，并完成有限赎回。
- 林见夏的命运得到明确落点，不使用模糊失踪或突然复活逃避结局。
- 第 80 章完成主线闭环，同时保留人物继续生活的余韵，不以新阴谋强行续订。

### 4.7 文风与章节约束

- 每章至少完成一个可观察的局势变化，不能只增加疑问。
- 每章最多引入一个新的核心规则或核心名词。
- 同一异常场景模板不得连续两章复用。
- 章末钩子必须来自人物选择、已知事实的新后果或具体危险，不使用旁白预告。
- 每四章至少有一次配角主动改变局势。
- 对话必须体现身份和关系，不让所有角色承担解释器功能。
- 禁止总结式复述本章发生了什么。
- 禁止为了“像人写”故意加入错别字、病句或无意义口语。
- 不模仿任何在世作者的可识别个人风格。

## 5. 作者模式产品设计

### 5.1 用户入口

项目工作台新增“作者稿”页签，提供三种输入方式：

1. 单章粘贴：填写章号、标题和正文。
2. 文件上传：导入单个 `.md` 或 `.txt` 文件。
3. 多章导入：使用现有长篇拆章解析能力，预览章号、标题、字符数和解析置信度后批量创建作者稿。

导入预览不写入正式章节。用户确认后才创建 Author Submission。

### 5.2 核心边界

- Author Submission 是作者提供的候选正文，不是 Final Chapter。
- 作者稿流程不调用 `writeDraftFromContext`，也不触发 Writer assignment。
- 审查流程必须接收明确的 `submissionId`、`contentHash` 和 `source`。
- 只有通过审查或由用户明确人工批准的 Submission 才能进入 Commit。
- Commit、版本文件和后续 Canon/Summary 仍复用现有统一链路。

### 5.3 数据模型

新增 `chapter_submissions`：

- `id`
- `project_id`
- `chapter_no`
- `title`
- `source`：`human | codex | import`
- `content_path`
- `content_hash`
- `status`：`draft | queued | reviewing | needs_revision | approved | committed | failed`
- `parent_submission_id`
- `committed_version_id`
- `created_at`
- `updated_at`

`committed` 是带血缘的终态：`committed_version_id` 必须引用同一项目、同一章的真实 Version。状态机中的 `approved → committed` 只能由同时接收 `versionId` 的专用原子操作完成；通用状态切换不得制造 `committed + NULL version`。

新增 `chapter_submission_batches`：

- `id`
- `project_id`
- `source_file_name`
- `source_file_hash`
- `chapter_count`
- `status`
- `created_at`

扩展 `review_reports`：

- `submission_id`
- `version_id`
- `content_hash`
- `reviewer_profile_id`
- `prompt_hash`
- `review_schema_version`

任何 Review Report 必须能证明它审查的是哪一份正文。

### 5.4 API

- `POST /api/projects/{projectId}/author-submissions/preview`
  - 输入粘贴文本或文件。
  - 返回解析后的章节清单、字符数、警告和重复章号冲突。
- `POST /api/projects/{projectId}/author-submissions/import`
  - 创建单章或批量 Submission。
  - 使用文件哈希保证幂等。
- `GET /api/projects/{projectId}/author-submissions`
  - 查询批次、章节状态和审查结果。
- `POST /api/projects/{projectId}/author-submissions/{submissionId}/review`
  - 进入作者稿审查流程。
- `POST /api/projects/{projectId}/author-submissions/{submissionId}/approve`
  - 明确人工批准，并通过统一 Commit 服务落盘。
- `POST /api/projects/{projectId}/author-submissions/{submissionId}/revise`
  - 创建新 Submission，保留父子版本关系。

所有写接口继续使用项目 ID、章号、会话状态和路径安全校验。

### 5.5 审查数据流

```text
Codex 正文
  → Author Submission
  → 确定性格式/长度/语病/重复检查
  → 组装 Review Context
  → Quick Review
  → 按策略强制 Deep Review
  → needs_revision 或 approved
  → Codex 修订或用户人工批准
  → Chapter Commit
  → Canon / Summary / Character Snapshot
  → 下一章
```

作者稿审查不得自动改写正文。Reviewer 只能返回问题、证据和修改建议；正文修订由 Codex 主代理完成。

## 6. 审查机制 P0 修复

### 6.1 记忆时序

生成或审查第 N 章之前，必须先确认第 N-1 章的 Canon、Summary、Character Snapshot 和 Logic State 已同步完成。Blueprint/ChapterPlan 也必须位于该等待之后。

### 6.2 强制深审策略

Opening、Mid Window、Cadence、Final Chapter、Manual Checkpoint 等强制触发条件独立于 LLM Quick Audit 是否运行。确定性 Quick Audit 通过不能绕过强制 Deep Review。

### 6.3 回滚边界

`earliestAffectedChapter` 必须满足：

```text
windowStartChapter <= earliestAffectedChapter <= currentChapter
```

超出窗口的模型输出视为非法，不得自动归档时间线。

### 6.4 Review Lineage

页面展示和自动决策只能消费与当前 `contentHash` 匹配的 Review Report。Patch、回滚或作者修订产生新哈希后，旧 Review 自动标记为 stale。

### 6.5 跨章重复与因果检查

新增确定性窗口检查：

- 段落和场景级 n-gram/指纹重复。
- 连续章节地点、人物在场状态和时间标记冲突。
- 同一规则说明、警告语、幻象或仪式场景的重复出现。
- 句子残缺、异常标点、缺谓语和错误占位文本。
- 章末总结句和“提出问题但没有推进”的空钩子。

确定性检查命中严重问题时不得被 LLM `pass` 覆盖。

### 6.6 Context 预算

Review Context 必须记录实际序列化长度和估算 token 数，不再把固定 128000 当作真实使用量。所有分区预算总和不得超过总预算。

### 6.7 Canon 部分成功

Summary、Facts、Character Snapshot 独立提交结果。单路失败只降级该路，并记录 `partial_success`，不得丢弃其他成功结果。

## 7. 错误处理与幂等

- 同一项目、章号和内容哈希重复导入时返回现有 Submission。
- 导入文件先写 staging，校验成功后原子移动到项目作者稿目录。
- 项目存在运行中的 Writer session 时，作者稿 Commit 默认拒绝；只允许进入草稿状态。
- Reviewer 超时或 JSON 校验失败时，Submission 保持 `needs_revision` 或 `failed`，不得静默通过。
- Commit 成功但 Canon 同步失败时，章节保持已提交，Artifact 状态显示部分失败并允许独立重试。
- Submission、Batch、Parent Submission 与 Version 的引用必须在仓储层验证项目/章号归属；内容身份重放只能复用不可变元数据兼容的记录，不能静默跨批次或跨修订血缘复用。
- Patch、回滚和作者稿 Commit 的未来时间线失效必须可重入；重试不能因为正文已变化而跳过尚未完成的 invalidation。
- 批量导入遇到单章失败时保留其他已验证 Submission，并返回逐章结果。

## 8. UI/UX 设计

### 8.1 作者稿页

- 顶部显示导入方式、当前批次和总章数。
- 中部使用虚拟列表展示 80 章状态。
- 每章显示字符数、内容哈希短码、审查状态、最新问题数和是否已提交。
- 支持筛选 `待送审 / 需修订 / 已通过 / 已提交 / 失败`。
- 危险操作必须确认：覆盖章号、提交新版本、回滚、归档未来章节。

### 8.2 章节工作台

- 小于 `xl` 时审稿和版本历史改为可访问抽屉，不得隐藏。
- Author Submission、Final Chapter 和历史 Version 明确标识，避免误以为草稿已定稿。
- Review 问题引用具体文本位置，并显示其对应的内容哈希。
- 支持在正文中选择文本后创建 Patch，替代裸字符偏移输入。
- 长任务提供取消、阶段、耗时和重试入口。

### 8.3 无障碍

- 抽屉、确认框和导入预览具备正确 dialog 语义、焦点陷阱、Escape 关闭和焦点恢复。
- 进度使用 `progressbar` 与 live region。
- 表单标签、错误信息和输入字段显式关联。
- 支持键盘完成导入、送审、查看问题和批准流程。

## 9. 写作与审查运行协议

1. Codex 主代理先完成全书故事圣经、人物状态表、规则表和 80 章标题/推进表。
2. 每次只创作一章最终候选正文，子代理不得代写。
3. 每章导入作者模式并运行确定性检查和 Quick Review。
4. 每 4 章强制 Deep Review 窗口。
5. 每 16 章执行卷级审计：人物弧、规则债务、伏笔、节奏、重复度和未回收承诺。
6. 出现硬连续性冲突时暂停后续写作，先修复最早受影响章节并重建后续状态。
7. 第 80 章通过终局审查后生成 Markdown 和 TXT 导出。

## 10. 测试设计

### 10.1 单元测试

- Author Submission Schema 与状态转换。
- 导入幂等和重复章号冲突。
- 多章解析与标题识别。
- Writer 永不被作者稿流程调用。
- 强制 Deep Review 不依赖 Quick Audit 调用门。
- `earliestAffectedChapter` 窗口约束。
- Review 与内容哈希匹配及 stale 标记。
- 跨章重复、句子残缺和人物在场冲突检测。
- Canon 三路部分成功。

### 10.2 集成测试

- 作者稿导入 → Review → 修订 → Commit → Artifact Sync。
- Commit 后崩溃恢复。
- Patch/回滚成功但 invalidation 首次失败后的重试。
- 上一章 Artifact 未完成时，下一章规划和审查必须等待。
- 80 章模拟 Submission 状态和查询性能。

### 10.3 E2E

## 11. 验收标准

### 11.1 产品

- 作者模式可从真实网页完成单章与批量导入。
- 作者稿流程的 Writer 调用次数为 0。
- 80 章均拥有 Submission、内容哈希、最终 Version 和可追溯 Review 状态。
- 每章至少运行一次确定性检查；每 4 章拥有 Deep Review 窗口记录。
- Review 不得显示或消费与当前正文哈希不一致的报告。
- 80 章导出成功，章节连续且无缺章。
- 关键 E2E 不再使用 `describe.skip`。

### 11.2 小说

- 正式章节不少于 80 章。
- 每章不少于 2200 个非空白中文正文字符。
- 总正文不少于 176000 个非空白中文正文字符。
- 五卷均完成卷级目标并有明确卷末变化。
- 主要人物命运、姐姐主线、档案局主线、能力代价和 04:17 规则均完成闭环。
- 不存在未处理的重大人物位置、时间、规则或身份冲突。
- 不存在连续两章复用同一异常场景模板。
- 最终人工通读结论达到“结构完整、语言自然、可作为正常商业网文阅读”。

## 12. 风险与控制

- **正文规模风险：** 采用单章创作、四章窗口、十六章卷审，不批量生成无人复核的大段正文。
- **审查成本风险：** 记录 Reviewer 和 Artifact 调用量；Writer 调用固定为零。
- **状态污染风险：** 使用全新项目；现有项目保持不变。
- **脏工作树风险：** 所有实现只改任务必需文件，提交时逐文件核对，不纳入用户现有未提交改动。
- **长任务恢复风险：** 通过 Submission 状态、内容哈希、版本和卷级进度文档恢复，不依赖会话记忆。
- **审查模型偏差：** Codex 人工审读作为金标准，平台 Review 作为被测对象，不用模型自评替代最终验收。
